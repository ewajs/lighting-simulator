# 0058. Accuracy checks: Lux Studio against Radiance

- **Status:** Accepted
- **Date:** 2026-10-16

## Context

ADR 0057 checks the illuminance maths against hand calculations and
conservation laws. Those prove the code does what we think, but not that
what we think matches how the lighting industry calculates. Lighting designers
will compare our numbers with DIALux, so we need references from tools that
don't share our code or our assumptions.

The owner asked for:
- tools that produce evidence to be committed, not throwaway scripts;
- Python allowed, through uv and the latest stable release (3.14);
- documented Python code, browsable in a web page.

## Decision

### Radiance as the reference

Radiance is the research lighting simulator from Lawrence Berkeley National
Laboratory. It's validated against the CIE 171 test cases like DIALux and
Relux, and has its own IES reader, `ies2rad`.
- **It runs locally:** a command-line program we can script, unlike DIALux
  (a Windows GUI) or AGi32 (paid).
- **Licence:** BSD-style (version 2.0), which allows our use. It is
  downloaded, never redistributed.
- **The release is pinned:** 6.0 patch 2 (`rad6R0P2`), by its SHA-256.
  Releases from 2026-02-20 until a fix on 2026-10-15 drop `ies2rad`'s
  multiplier (`source_corr` tested `nrargs > 1` where it meant `>= 1`).
  That makes every IES light 1/area too dark: 55× for the demo's downlight.
- **macOS on Apple silicon only**, the build the checks were verified with.

### Radiance is checked before it's trusted

`accuracy check` places each IES file alone and measures it 20 m away,
where the illuminance is I / d², with I read from the file by our own small
Python reader.
- **What it checks:** the reading, the units and the orientation.
  - Each demo file is checked as a point-source copy, which isolates those
    from how Radiance models a large opening's area. Radiance samples a
    box-shaped opening up to 2 % off even far away, straight up.
  - A made-up lopsided distribution at five aims checks our mapping of
    tilt and pan into Radiance's Z-up coordinates and its `xform` rotations.
- **Result:** all 194 checks within 0.001 %.
- **Proof it catches the bug:** a test runs the checks on the buggy release
  (`39b99660`, also pinned), and every check fails.
- **No reference is written** unless every check passes.

### Five reference rooms, direct light

| Room | What it tests |
|---|---|
| A single downlight | the basic case |
| Four downlights and a wall washer | several lights at once, and an asymmetric distribution |
| Two narrow track spots, tilted and panned | aim, pan and a 17° beam |
| A 1.2 m linear pendant over a table top | close to a large opening, and a shadow |
| An up/down wall sconce | a 51 cm glowing box very close to its wall |

Each room is a JSON file in Lux Studio's coordinates:
- each luminaire's IES file, light origin, tilt and pan;
- shadow boxes, given as boxes;
- measuring grids.

Radiance writes its lux at every point to `accuracy/references`, 5,726
points in all, with the release, options and date.

### The comparison

`accuracy/typescript` (an npm workspace) rebuilds each room with core's own
functions and compares every point. Its tolerances are regression bounds set
from the measured agreement:

| Check | Tolerance | Measured worst |
|---|---|---|
| Each surface's average | 1 % | 0.56 % |
| Bright points (≥ 10 % of the room's maximum) at least 1 m from a luminaire | 3.5 % | 3.0 % |
| Bright points nearer than 1 m | 15 % | 12.7 % |

Outside the wall sconce's room, every bright point is within 2 %.
`accuracy/REPORT.md` holds the figures, and `accuracy/summary.json` the same
as data for the manual (ADR 0059), both regenerated by
`npm run accuracy:report`. A test fails if either is stale.

**What it found.** Openings were split in width and length but not height
(ADR 0057). Next to the sconce, points read up to 60 % off. They are now
split in height too, and the worst point fell to 12.7 %.

The rest is two tools approximating a glowing box differently: Radiance
makes its surface glow, we spread the light over cells inside it. An IES
file describes the far field only, so neither is the luminaire's true near
field.

### The Python, and its standards

```
accuracy/
  README.md          how to run it all and read the results
  REPORT.md          the comparison's figures (generated)
  rooms/             the reference rooms (hand-written)
  references/        Radiance's values (generated, committed)
  python/            uv project, Python 3.14: luxstudio_accuracy
  typescript/        npm workspace: the comparison and the real-file evidence
```

- **Dev dependencies only:** ruff (lint, format, and Google-style
  docstrings on every public module, class and function), mypy (strict),
  pytest, pdoc. No runtime dependencies.
- **Docs:** pdoc turns the docstrings into HTML at `/docs/accuracy/`,
  linked from the TypeDoc site's navigation. `npm run accuracy:docs`
  serves them locally.
- **Commands:**
  - `npm run accuracy:check` runs ruff, mypy and pytest.
  - `npm run accuracy:references` regenerates the references and the report.
  - `npm run accuracy:report` regenerates only the report.
- **CI** installs uv and runs `accuracy:check`. Off macOS, the Radiance
  tests skip and say so. The references and the report are regenerated
  locally, like the e2e suite.

## Options considered

- **DIALux as the only reference.** It's the tool designers use, but it's a
  Windows GUI that can't be scripted. It stays the final check (M5.5).
- **Radiance in Docker.** Its Linux build would run in CI, but under
  emulation on Apple silicon, and it's another moving part. The native
  macOS build is enough for now.
- **Checking the demo files with their real openings.** Radiance's own
  area-source errors (up to 2 %) would hide or mimic the mistakes the
  checks are for.
- **The comparison in Python.** That would mean reimplementing Lux
  Studio's calculation. The point is to test that calculation itself, so
  the comparison runs it in TypeScript.
- **The name "validation" or "benchmark".** "Benchmark" clashes with
  `npm run bench` (speed); the owner preferred "accuracy".

## Consequences

- A second toolchain: uv and Python 3.14 locally and in CI.
- The references are about 1 MB of committed JSON. They change only when a
  room or the Radiance release does, and the report shows any change.
- Bounce light (M5.3) adds the room's surfaces to the scenes and extends
  the same rooms.
- `npm test` runs the comparison with the other unit tests, in about 5 s.
